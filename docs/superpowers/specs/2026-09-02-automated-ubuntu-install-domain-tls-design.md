# GearVia Ubuntu 자동 설치 및 도메인·SSL 운영 설계

작성일: 2026-09-02

## 목표

Ubuntu 24.04 LTS 서버에서 다음 명령 하나로 GearVia 단일 노드 구성을 설치한다.

```bash
sudo ./install_gearvia_ai_agent_ubuntu.sh
```

사용자가 직접 `runtime.env`, JWT 비밀값, MFA 암호화 키, TLS 인증서 또는 Docker 이미지
식별자를 준비하지 않아도 되어야 한다. 설치 중 사용자가 입력하는 필수값은 번들 MySQL의
애플리케이션 비밀번호 하나로 제한한다. 도메인과 운영 인증서는 설치 후 관리자 페이지에서
안전하게 변경한다.

## 결정 사항

### 1. 설치 입력과 비밀정보

- 기본 설치는 터미널에서 MySQL 애플리케이션 비밀번호를 숨김 입력으로 두 번 받는다.
- CI 및 무인 설치는 `--db-password-file /absolute/path`만 지원한다. 명령행 인자와 일반 환경
  변수로 비밀번호를 받지 않아 프로세스 목록과 셸 기록 노출을 막는다.
- `JWT_SECRET`, `ADMIN_MFA_ENCRYPTION_KEY_BASE64`, MySQL root 비밀번호는 시스템 CSPRNG로
  각각 생성한다. OpenSSL을 우선 사용하고 요구 길이를 검증한다.
- 설치기가 `/etc/gearvia/runtime.env`를 직접 만들며 권한은 root 전용 `0600`으로 설정한다.
  저장소의 예제 `.env`를 복사하거나 평가하지 않는다.
- 재실행 시 기존 비밀값과 DB 비밀번호를 유지한다. `--rotate-secrets` 같은 자동 회전 기능은
  이번 범위에 포함하지 않는다.

### 2. 서버 주소와 초기 TLS

- 설치기는 기본 경로의 IPv4 주소와 호스트 이름을 감지한다. 초기 공개 URL은
  `https://<감지된-IP>`를 사용한다.
- 설치 시 로컬 CA와 서버 인증서를 자동 생성한다. 서버 인증서 SAN에는 감지된 IP,
  호스트 이름, `localhost`, `127.0.0.1`을 포함한다.
- 로컬 CA 개인 키, 서버 개인 키와 인증서는 `/etc/gearvia/tls`에 root 전용 권한으로 보관하고,
  Nginx에는 읽기 전용으로 마운트한다.
- 설치 완료 화면에는 접속 URL과 클라이언트에 배포할 CA 인증서 경로를 표시한다.
- 인터넷이 차단된 사내망을 기본 전제로 하므로 Let's Encrypt 자동 발급은 포함하지 않는다.

### 3. Docker 이미지 자동 준비

설치기는 다음 우선순위로 이미지를 준비한다.

1. 릴리스 번들의 `infra/images/*.tar`가 있으면 `docker load`로 로드한다.
2. 필요한 애플리케이션 이미지가 로컬에 있으면 재사용한다.
3. 없으면 저장소의 `backend/Dockerfile`, `frontend/Dockerfile`로 자동 빌드한다.
4. MySQL 8.x와 초기화 이미지는 로컬에 없으면 승인된 레지스트리에서 가져온다.

이미지 이름은 사용자가 입력하지 않는다. 애플리케이션 이미지는 Git 커밋 기반의 고정 태그를
사용하고, 설치 완료 시 이미지 ID와 가능한 경우 레지스트리 다이제스트를 설치 상태 파일에
기록한다. 외부 접속이 차단된 환경에서 이미지 번들과 캐시가 모두 없으면 필요한 이미지 이름을
명확히 출력하고 호스트를 변경하지 않은 채 중단한다.

### 4. 설치 트랜잭션과 재실행

설치 순서는 사전 점검, 입력 수집, 비밀값 생성, 이미지 준비, 후보 설정 생성, Compose 검증,
파일 원자적 배치, 서비스 시작, 준비 상태 검사 순서다. 후보 검증 전에는 기존 운영 파일을
바꾸지 않는다.

업그레이드 또는 재설치에서 서비스 시작이나 준비 상태 검사가 실패하면 직전
`runtime.env`, 인증서 및 Compose 파일을 복구하고 기존 서비스를 다시 시작한다. 처음 설치가
실패하면 새로 생성한 활성 설정과 인증서를 제거하되 진단 로그는 남긴다.

Docker Engine과 Compose v2는 필수 기반 소프트웨어다. 설치기는 존재 여부와 버전을 검사하고,
없으면 승인된 사내 저장소 또는 별도 설치가 필요하다는 한글 오류를 반환한다. 임의의 외부 저장소를
자동 등록하지 않는다.

### 5. 관리자 도메인·SSL 설정

관리자 메뉴에 **도메인·SSL 설정** 페이지를 추가한다.

- 현재 공개 URL, 인증서 발급자, 유효기간, SAN 및 적용 상태를 표시한다.
- 도메인 또는 IP를 입력하고 **연결 테스트**를 실행할 수 있다.
- 사내 CA가 발급한 인증서와 개인 키를 함께 업로드할 수 있다. 개인 키는 API 응답이나 로그에
  반환하지 않는다.
- 별도 인증서를 올리지 않으면 새 주소용 자체 서명 서버 인증서를 로컬 CA로 자동 재발급한다.
- 도메인 형식, DNS/IP 해석 결과, 인증서 유효기간, SAN, 인증서·개인 키 일치 여부를 적용 전에
  검사한다.
- 테스트 성공 후에만 **적용** 버튼을 활성화한다. 적용 시 예상 중단 시간을 표시하고 기존 공지
  체계를 사용해 전체 사용자에게 알린다.
- 적용 결과와 요청 관리자를 감사 로그에 남기며 비밀키와 인증서 본문은 기록하지 않는다.

공개 URL은 DB의 단일 설정으로 관리하고 CORS, 상태 변경 동일 출처 검사, WebSocket 허용 출처,
초대 링크 및 비밀번호 재설정 링크가 같은 동적 설정을 사용한다. Nginx `server_name`은 사내
배포에서 임의 호스트를 받을 수 있게 유지하고, 승인된 공개 URL은 애플리케이션 계층에서
검증한다.

### 6. 호스트 권한 경계

백엔드 컨테이너에 Docker 소켓이나 root 권한을 제공하지 않는다. 백엔드는 제한된 공유 요청
디렉터리에 검증된 변경 요청을 기록한다. root 소유 systemd 적용 도우미가 다음 작업만 수행한다.

1. 요청 서명·권한·경로와 인증서 쌍을 다시 검증한다.
2. 후보 인증서와 런타임 URL을 원자적으로 배치한다.
3. Nginx 설정 검사를 수행하고 웹 컨테이너를 재생성한다.
4. HTTPS 준비 상태와 새 인증서를 확인한다.
5. 실패 시 이전 파일과 URL을 복원하고 결과 파일을 기록한다.

도우미는 고정 경로와 허용된 명령만 사용한다. 임의 셸 문자열, 임의 파일 경로 또는 임의 Docker
명령을 요청에서 받지 않는다. 기존 `InfrastructureChangeJob`에 `DOMAIN_TLS` 유형을 추가해
테스트, 공지, 적용, 검증, 완료 또는 롤백 상태를 추적한다.

### 7. 제거와 재설치

기본 제거는 서비스와 GearVia 컨테이너를 중지하고 다음 활성 파일을 제거한다.

- systemd 서비스 및 적용 도우미
- `/etc/gearvia/runtime.env`
- `/etc/gearvia/tls`의 자동 생성 또는 업로드 인증서와 개인 키
- 설치된 Compose 및 제어 요청 파일
- GearVia가 빌드한 애플리케이션 이미지 태그

MySQL 볼륨, 업로드/NAS 데이터와 root 전용 복구 상태는 기본 제거에서 보존한다. 기존 MySQL
볼륨을 재사용하는 경우 DB 비밀번호가 달라지면 접속할 수 없으므로, 재설치기는 보존된 복구
상태에서 DB 인증정보만 다시 사용한다. `--purge-data --confirm-purge GEARVIA`를 지정하면 복구
상태와 GearVia 관리 데이터까지 삭제한다. 외부 NAS의 파일은 절대 자동 삭제하지 않는다.

## 오류 처리

- 비밀번호 불일치, 빈 값 또는 제어문자 포함 시 입력 단계에서 다시 요청한다.
- 주소 감지 실패 시 사용 가능한 사설 IP 목록을 보여 주고 하나를 선택하게 한다.
- 인증서 생성·검증 실패 시 서비스 파일을 설치하지 않는다.
- 이미지 준비 실패 시 이미 준비된 기존 서비스와 이미지를 변경하지 않는다.
- 관리자 변경은 중복 요청을 correlation ID로 막고 낙관적 잠금으로 동시 관리자 충돌을 막는다.
- 호스트 도우미 응답이 제한 시간을 넘으면 실패로 표시하고 기존 서비스 상태를 유지한다.

## 데이터 모델과 인터페이스

- Flyway V7에서 `deployment_settings` 단일 행 테이블을 추가한다. 공개 URL, 인증서 메타데이터,
  적용 버전, 상태 및 갱신 시각만 저장한다. 개인 키와 인증서 본문은 DB에 저장하지 않는다.
- 관리자 API는 상태 조회, 연결 테스트, 인증서 업로드를 포함한 변경 초안 생성, 적용 요청 및
  적용 결과 조회로 분리한다.
- 프런트엔드는 관리자 전용 페이지와 진행 상태 표시를 제공하고 한글/영문 문자열을 함께 둔다.
- 설치 상태 파일에는 설치 버전, Git 커밋, 이미지 ID, 활성 주소, 생성 파일 목록만 저장하며
  비밀값은 기록하지 않는다.

## 시험 전략

- Bash 수명 주기 시험: 무인자 실행, 숨김 입력 대체용 비밀번호 파일, 비밀값 형식, 재실행 시
  보존, 인증서 SAN, 이미지 선택 우선순위, 실패 원자성, 일반 제거 및 완전 삭제를 검사한다.
- Compose 시험: 사용자 이미지 변수가 없어도 생성된 설정으로 병합·검증되는지 확인한다.
- 백엔드 단위/API 시험: 동적 공개 URL 사용처, 관리자 권한, 주소·인증서 검증, 상태 전이,
  감사 로그 및 롤백을 검사한다.
- 프런트엔드 시험: 현재 상태 표시, 테스트 성공 전 적용 금지, 인증서 파일 입력, 적용 진행과
  실패 메시지를 검사한다.
- 통합 시험: Ubuntu 24.04 VM의 초기 설치, 같은 버전 재실행, 업그레이드, 도메인 변경,
  인증서 교체, 강제 실패 롤백, 제거 후 데이터 보존 재설치를 수행한다.

## 완료 기준

- 새 Ubuntu 호스트에서 외부 설정 파일 없이 무인자 설치를 시작할 수 있다.
- MySQL 애플리케이션 비밀번호 외의 필수 비밀값과 초기 SSL이 자동 생성된다.
- 이미지 번들 또는 빌드 가능한 소스 중 하나가 있으면 이미지 식별자 입력 없이 설치된다.
- 관리자 페이지에서 도메인·SSL 시험과 적용을 수행하고 실패 시 이전 HTTPS 접속이 복구된다.
- 기본 제거 후 인증서와 활성 설정은 사라지며 데이터 보존 재설치가 가능하다.
- 기존 백엔드·프런트엔드 테스트와 Ubuntu 수명 주기 검증이 모두 통과한다.
