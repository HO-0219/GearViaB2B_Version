# 그룹 업무 탐색 및 동적 SMTP 설정 설계

## 목표

그룹 대시보드에서 업무 목록으로 바로 이동할 수 있게 하고, 업무와 알림을 서버 기준으로 필터링하며, 운영자가 재배포 없이 SMTP 연결 정보를 저장·검증·활성화할 수 있게 한다.

## 범위

- 그룹 대시보드 상단의 `파일` 링크 옆에 `업무 목록` 링크 추가
- 그룹 업무 목록에 검색어, 상태, 우선순위, 프로젝트, 담당 범위, 마감 상태 필터 추가
- 알림 목록의 기존 읽음 상태·그룹 필터를 서버 필터로 전환하고 알림 유형·기간 필터 추가
- `mail_settings` 단일 행과 관리자 SMTP 설정 API·화면 추가
- `JavaMailSenderImpl`을 런타임 설정으로 만드는 `MailSenderFactory` 도입
- 관련 백엔드·프런트엔드 테스트와 운영 설정 문서 갱신

## SMTP 설정 모델

`mail_settings`는 애플리케이션 전체가 공유하는 단일 행 테이블이다. 컬럼은 다음과 같다.

| 컬럼 | 의미 |
| --- | --- |
| `id` | 고정값 `1` |
| `host` | SMTP 서버 호스트 |
| `port` | SMTP 서버 포트 |
| `username` | 인증 사용자명, 선택 입력 |
| `encrypted_password` | AES-GCM으로 암호화한 비밀번호, 선택 입력 |
| `smtp_auth` | SMTP AUTH 사용 여부 |
| `starttls` | STARTTLS 사용 여부 |
| `from_address` | 발신자 주소 |
| `enabled` | 실제 메일 발송 여부 |
| `updated_at` | 마지막 변경 시각 |

비밀번호 암호화에는 기존 `AdminMfaCipher`와 `ADMIN_MFA_ENCRYPTION_KEY_BASE64`를 재사용한다. API는 평문·암호문을 반환하지 않고 `passwordConfigured`만 반환한다. 업데이트 요청에서 비밀번호 필드를 생략하면 기존 값을 유지하고, 빈 문자열이면 삭제하며, 값이 있으면 교체한다. AUTH가 활성화된 상태에서 사용자명이나 비밀번호가 없으면 활성화를 거부한다.

## 설정 우선순위와 메일 발송

관리자가 SMTP 설정을 한 번도 저장하지 않아 DB 행이 없으면 기존 `spring.mail.*`, `app.mail.from`, `app.mail.enabled` 값을 초기 대체 설정으로 사용한다. DB 행이 생성된 이후에는 DB 값이 유일한 기준이며, `enabled=false`일 때 환경변수로 우회하지 않는다.

`MailSenderFactory.createSender()`는 현재 유효 설정을 읽고 `JavaMailSenderImpl`에 host, port, username, 복호화한 password, SMTP AUTH, STARTTLS를 설정한다. 호출 결과에는 sender와 발신 주소가 함께 제공되어 발신 설정이 서로 어긋나지 않게 한다. 현 단계에서는 정확성과 단순성을 위해 발송마다 DB 설정을 조회하고 sender를 생성한다. 발송량 증가 시 `updated_at` 기반 캐시를 추가할 수 있으나 이번 범위에는 포함하지 않는다.

`MailService`는 고정 `JavaMailSender` 주입을 제거하고 각 발송 시 factory를 호출한다. 설정이 비활성이면 기존 로컬 로그 동작을 유지한다. 설정 조회·복호화·전송 실패는 기존 best-effort 계약대로 회원가입, 복구, 초대, 리포트 등의 주 트랜잭션을 롤백하지 않는다. 로그에는 수신자 마스킹 값과 오류 종류만 남기고 자격 증명은 남기지 않는다.

## 관리자 SMTP API와 화면

관리자 전용 `/api/v1/admin/mail-settings`에 다음 동작을 제공한다.

- `GET`: 현재 유효 설정과 설정 출처(`DATABASE` 또는 `ENVIRONMENT`), 비밀번호 설정 여부 조회
- `PUT`: 설정 검증 후 DB 단일 행 저장
- `POST /test`: 저장 후보값 또는 현재 설정으로 SMTP 연결과 인증 테스트

테스트는 메일을 실제 수신자에게 보내지 않고 JavaMail 연결 검증을 사용한다. 테스트 실패는 이해 가능한 메시지로 반환하되 비밀번호, 서버 응답의 민감한 내용, 상세 스택은 노출하지 않는다. 저장 자체는 테스트 성공을 강제하지 않아 방화벽이 아직 열리지 않은 설치 단계도 지원한다. 활성화 요청은 필수 필드와 암호화 키 조건을 만족해야 한다.

관리자 화면에는 `SMTP 설정` 탭과 통합 화면 섹션을 추가한다. host, port, username, password, SMTP AUTH, STARTTLS, 발신 주소, 활성화 여부를 편집하며, 비밀번호는 빈 입력 상태로 표시하고 기존 설정 여부만 안내한다. 저장과 연결 테스트는 독립 버튼으로 제공하고 결과를 화면에 표시한다. 관리자 접근 제어·MFA·감사 필터는 기존 `/api/v1/admin/**` 규칙을 그대로 적용한다.

## 그룹 대시보드 링크

`GroupDashboardPage` 상단 작업 영역에서 기존 `파일` 링크 다음에 `업무 목록` 링크를 추가하고 `/groups/{groupId}/tasks`로 이동시킨다. 기존 라우트를 재사용하며 권한 검사는 업무 API에서 유지한다. 작은 화면에서도 기존 작업 버튼 레이아웃이 자연스럽게 줄바꿈되도록 관련 스타일을 확인한다.

## 업무 필터

업무 API는 다음 선택 쿼리 파라미터를 받는다.

- `query`: 제목과 설명의 대소문자 무시 부분 검색
- `status`: 하나의 업무 상태
- `priority`: 하나의 우선순위
- `projectId`: 그룹 내 프로젝트
- `assignment`: `ALL`, `MINE`, `UNASSIGNED`
- `due`: `ALL`, `OVERDUE`, `DUE_SOON`

`DUE_SOON`은 현재 시각부터 7일 이내이며 완료·반려·취소 업무는 마감 필터에서 제외한다. 기존 기본 호출은 모든 조건이 비어 있는 것과 동일하게 동작하여 호환성을 유지한다. 필터는 권한 확인 후 저장소 쿼리에 적용한다.

프런트엔드는 필터를 URL 쿼리스트링에 저장한다. 검색 입력은 짧은 debounce 후 요청하고, 나머지 필터 변경은 즉시 첫 목록을 다시 조회한다. 프로젝트 선택지는 현재 그룹의 활성 프로젝트에서 제공한다. 필터 초기화 버튼과 필터 결과 건수를 표시한다. 기존 `projectId`, `topicId`, `create=1` 생성 모달 파라미터와 충돌하지 않게 별도 필터 키를 사용한다.

## 알림 필터

알림 API는 기존 cursor 페이지네이션에 다음 조건을 추가한다.

- `read`: `ALL`, `READ`, `UNREAD`
- `groupId`: 특정 그룹
- `type`: 특정 알림 유형
- `period`: `ALL`, `TODAY`, `LAST_7_DAYS`, `LAST_30_DAYS`

조건은 사용자 소유권 조건과 함께 DB 쿼리에 적용되어 페이지 사이에서도 일관된 결과를 반환한다. `unreadCount`는 필터 결과가 아니라 사용자의 전체 읽지 않은 알림 수를 유지해 전역 배지와 일치시킨다. 그룹 선택지는 현재 로드된 페이지에서 추론하지 않고 사용자가 속한 그룹 목록을 이용한다.

프런트엔드는 기존 읽음·그룹 UI를 유지하면서 유형·기간 선택을 추가한다. 필터가 바뀌면 누적 항목과 cursor를 초기화하고 첫 페이지를 요청한다. 실시간 갱신과 30초 폴링도 현재 필터를 유지한다.

## 오류 처리와 보안

- SMTP 비밀번호는 요청 DTO 외의 응답, 로그, 감사 데이터에 포함하지 않는다.
- 암호화 키가 없거나 저장 비밀번호를 복호화할 수 없으면 설정을 비활성 상태로 취급하고 관리자에게 재입력을 안내한다.
- host 길이, port 범위, 발신 주소 형식, 인증 필드 조합을 서버에서 검증한다.
- SMTP 연결 테스트에는 제한된 연결·읽기 timeout을 설정해 관리자 요청이 장시간 정지하지 않게 한다.
- 업무와 알림 필터 값은 enum과 숫자로 엄격히 검증하고 접근할 수 없는 그룹·프로젝트 조건은 기존 권한 정책에 따라 거절한다.

## 데이터베이스 변경

현재 프로젝트의 단일 Flyway 기준 스키마에 `mail_settings`를 추가한다. 기존 배포 DB에 적용 가능한 별도 증분 마이그레이션이 이미 운영 관례로 존재하는지 구현 시작 시 확인하고, 필요하면 다음 버전 마이그레이션도 함께 제공한다. JPA는 운영 환경에서 `validate`를 사용하므로 테이블과 엔티티 정의를 정확히 맞춘다.

## 테스트

- DB 설정 부재 시 환경변수 대체, DB 설정 우선, 명시적 비활성화 검증
- SMTP 비밀번호 암호화·유지·삭제·복호화 실패와 응답 비노출 검증
- `JavaMailSenderImpl` 속성 매핑과 연결 테스트 성공·실패 검증
- 메일 실패가 호출자 트랜잭션에 영향을 주지 않는 기존 계약 회귀 테스트
- 관리자 SMTP API 접근 제어, 입력 검증, 감사 대상 검증
- 업무 필터별 저장소/API 결과와 그룹 권한 검증
- 알림 필터와 cursor 페이지네이션, 전체 unread count 검증
- 대시보드 업무 링크, 업무 필터 URL 유지, 알림 필터 초기화·재조회 UI 테스트
- 백엔드 전체 Maven 테스트와 프런트엔드 테스트·프로덕션 빌드

## 제외 범위

- SMTP 서버 제공자별 OAuth2 인증
- 여러 SMTP 프로필 또는 그룹별 SMTP 설정
- 메일 큐·재시도 시스템의 재설계
- sender 캐시와 다중 인스턴스 캐시 무효화
- 업무 필터의 복수 상태·복수 우선순위 선택
